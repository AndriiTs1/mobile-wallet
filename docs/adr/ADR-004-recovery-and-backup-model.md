# ADR-004: Recovery & Backup Model

**Status:** Accepted

**Scope:** This ADR decides the recovery/backup *policy* layer on top of the derivation *structure* already fixed by ADR-003: what recovery secret exists, how it is generated, how it is backed up and (optionally) revealed, whether a passphrase is offered, how import/restore behaves, and what the product's trust boundary guarantees about recovery independent of Swiss Wallet's own infrastructure. It does not decide Rust crate selection, secure-storage implementation details, biometric library choice (ADR-005), or RPC/indexer/provider strategy (Stage 4C / a future provider ADR). It builds directly on **ADR-002** (Wallet Core runtime and trust boundary) and **ADR-003** (account, derivation and address model), and does not weaken either.

---

## Context

ADR-002 established that Wallet Core is a single shared Rust implementation owning the mnemonic/seed lifecycle, that seed/private keys never cross into React Native or the backend, and that no signing occurs off-device. ADR-003 established that V1 uses one BIP-39 seed as the root for a single BIP-32 HD tree, with standard Ethereum (`m/44'/60'/0'/0/0`) and Bitcoin BIP-84 (`m/84'/0'/0'/0/i` external, `m/84'/0'/0'/1/i` internal) branches, and that recovery UX/policy was explicitly deferred to this ADR (ADR-003 §1, §29–31, §234–244).

Root `CLAUDE.md` and `apps/mobile/CLAUDE.md` require: seed phrases and equivalent wallet secrets must never be transmitted to a backend, logged, or placed in analytics/crash reports/screenshots/debugging output; must never use `AsyncStorage` or unprotected persistence; and any change touching wallet creation/import, recovery-phrase handling, or biometrics requires explicit security review. `docs/PRODUCT_ARCHITECTURE.md` §9 already sketches (as proposed, not-yet-approved architecture) the three-moments framing this ADR formalizes: initial backup/verification, later-reveal capability, and import/restore as distinct flows that must not be conflated — and explicitly defers cloud/social recovery to its own ADR with its own threat model (§9, §27 — listed there as ADR-004).

Today, no onboarding flow, no wallet-core, and no secure-storage integration exist in the repository (verified: `apps/mobile` contains no crypto/security dependencies; `packages/` is empty). This ADR decides recovery policy before any of that is implemented.

---

## Decision

### 1. Recovery standard

V1 recovery root: a **BIP-39 mnemonic**, expanded to a seed, feeding the single BIP-32 HD tree already fixed by ADR-003. One seed restores every V1 chain/account exactly as ADR-003 defines — there is no separate recovery mechanism per chain.

**Why BIP-39 is selected**: it is the de facto universal standard for HD wallet recovery — implemented by virtually every mainstream Bitcoin and Ethereum wallet, with a fixed, published word-to-entropy encoding and a built-in checksum. Choosing anything proprietary here would directly undermine the interoperability goal already established in ADR-003 §11, for no offsetting security benefit (the *encoding* of a mnemonic is not a secret and provides no security-through-obscurity value).

**Interoperability implications**: a BIP-39 mnemonic generated by Swiss Wallet can, in principle, be imported into any other BIP-39-compatible wallet, and vice versa — subject to that wallet also using the same derivation path/script-type conventions ADR-003 already documents this caveat for (ADR-003 §11: standard paths maximize compatibility, they do not guarantee universal automatic discovery).

**What BIP-39 does and does not guarantee**: BIP-39 guarantees that the *same words + the same optional passphrase* deterministically reproduce the *same seed*, every time, in any correct implementation — this is the entire basis for recovery working at all. **BIP-39 does not itself encode which chains, derivation paths, or accounts to derive from that seed.** The mnemonic is not chain-aware and carries no network/chain metadata — recovery only succeeds when the *same derivation and account policy* (ADR-003) is applied on top of the reconstructed seed. A correct mnemonic paired with a different or nonstandard derivation policy would silently reconstruct a *different* wallet with no funds visible, not an error — this distinction matters directly for §15 (Failure States) below.

**Relationship to BIP-32/BIP-84/ADR-003**: BIP-39 produces the seed; BIP-32 defines the HD tree structure that seed roots; ADR-003 is the specific, fixed choice of which branches of that tree V1 actually uses (BIP-44 coin_type 60' for Ethereum, BIP-84 coin_type 0' for Bitcoin). This ADR does not restate or alter any of ADR-003's path decisions — it only decides the policy around the BIP-39 layer beneath them.

### 2. Wordlist policy

**V1 generates English BIP-39 mnemonics only.**

Reasoning:
- **Ecosystem compatibility**: the English wordlist is the most universally implemented and tested across wallets, hardware devices, and recovery tooling — selecting it maximizes the odds that a restored mnemonic behaves identically everywhere.
- **Restore compatibility**: non-English BIP-39 wordlists have a documented history of implementation inconsistency (e.g. Unicode normalization differences affecting the Japanese wordlist's checksum behavior across implementations) — adopting English-only for V1 removes an entire class of restore-compatibility bugs before they can occur.
- **Reduced localization ambiguity**: recovery words are security-critical literal strings a user must transcribe exactly; translating or localizing them multiplies transcription-error surface and support burden for no compensating benefit.

**The app UI may be localized independently of this decision.** Menu text, instructions, and security explanations around the recovery phrase can be presented in any supported UI language — only the mnemonic words themselves are English-only in V1. No custom wordlist is invented; V1 uses the standard, published BIP-39 English wordlist exactly as specified.

Import validation in V1 is scoped to the same English wordlist used for generation (§8). Accepting import of mnemonics generated in other official BIP-39 wordlists is not rejected outright as a future possibility, but is **deferred** — it adds real validation-locale complexity for a case with no known V1 product requirement, and can be revisited if a specific need emerges.

### 3. 12 vs. 24 words

| | A. 12-word | B. 24-word |
|---|---|---|
| BIP-39 entropy | 128 bits | 256 bits |
| Transcription/error burden | Lower — half the words to write down and verify | Materially higher — roughly double the transcription surface and time |
| Backup UX | Faster onboarding, shorter verification challenge | Slower, more error-prone onboarding; higher abandonment risk |
| Practical security implication | 128 bits already vastly exceeds any brute-force feasibility for the foreseeable future — comparable in magnitude to widely-trusted symmetric-key security margins (e.g. AES-128) | Provides a larger theoretical margin, but for this threat model the marginal security benefit over 128 bits is not the limiting factor in wallet compromise (device compromise, phishing, and physical theft dominate real-world loss, not seed brute-forcing) |
| Interoperability | Fully standard, universally supported | Fully standard, universally supported |

**V1 default: 12 words, generated on wallet creation.** 128 bits of entropy is not a meaningfully weaker practical security posture for this threat model, and the reduced transcription/verification burden directly reduces the most common real-world failure mode in wallet onboarding — a user mis-recording or abandoning backup of a longer phrase. This is a deliberate usability-security balance, not a security compromise.

**No user-facing 12/24 generator selector is exposed in V1.** Offering a choice at creation time adds a decision the median user is not equipped to evaluate correctly, for a security difference that is not the actual limiting factor in this threat model — this is exactly the kind of speculative complexity the project's change-discipline principles caution against absent a compelling product reason, and none is identified here.

**24-word mnemonics remain importable** (§8) — a user migrating from another wallet that generated 24 words must be able to restore into Swiss Wallet without being told their existing backup is unsupported. The 24-word form is recorded here as **compatible/importable, not generatable**, in V1.

### 4. Onboarding backup flow

Conceptual V1 sequence:

```
wallet creation
  → recovery phrase generated on-device (12 English words, per §2–3)
  → explicit security explanation shown (what this phrase is, why it matters,
    what Swiss Wallet can never do with it, what happens if it is lost)
  → phrase displayed
  → user records phrase offline
  → verification/challenge (user re-enters a small random subset of the
    displayed words, e.g. words at 3–4 randomly selected positions)
  → acknowledgement (explicit, deliberate confirmation step — not a
    pre-checked box)
  → wallet marked backup-verified (locally, per §11)
```

**What "verified" means, precisely**: successful completion of the verification challenge proves only that the user could **accurately reproduce the requested words at that specific moment**, immediately after being shown the phrase. **It does not, and must not be represented as, proof that the user made a durable physical backup, stored it safely, or will still have access to it in the future.** The product's own copy and any internal status flag must not overstate what this checkpoint actually establishes.

**Skip-for-now assessment and decision**: a "skip for now" path was considered and explicitly rejected for V1. The wallet's Ethereum and Bitcoin receive addresses exist, and are capable of receiving funds, as soon as keys are derived — before backup verification would occur. A silent or easily-dismissed skip path risks a user holding real funds in a wallet they never actually confirmed they could back up, with no company-side fallback if the device is then lost (per §16). Given the irreversibility already established throughout this ADR series (no custodial reset, ever), **V1 requires backup verification to complete before onboarding is considered finished**, and does not offer a path that leaves a user holding an unbacked-up wallet under the impression that recovery is otherwise protected. This is a deliberate friction/safety tradeoff, accepted because the cost of getting it wrong (irrecoverable fund loss) is categorically worse than the cost of a slightly longer onboarding flow.

### 5. Later reveal policy

Decision: **B — the mnemonic can be revealed later, through a strictly gated, highly privileged local flow.** (Not A — permanent non-revealability after onboarding.)

Required conceptual properties of that flow:

- Explicit entry only through a dedicated **Recovery & Backup** surface — never reachable incidentally from another screen.
- Strong local authentication (biometric/passcode) required immediately before reveal, every time — no caching, no "remember for N minutes."
- A high-risk warning shown before reveal, restating what exposure of this phrase means.
- **No automatic display on navigation** — arriving at the Recovery & Backup screen must never itself show the phrase; the user must take a further, deliberate action to reveal it.
- Re-authentication is required again after any timeout or after the app has been backgrounded, even mid-flow.
- The mnemonic **disappears from the screen when the user leaves the flow or the app is backgrounded** — it is never left visible in a background/app-switcher snapshot or after navigating away.
- **Never copied to the clipboard automatically**, and (per §6) not offered as a manual copy action either.
- **No analytics, logging, or crash-reporting breadcrumbs** may reference this flow's content, timing beyond coarse non-identifying events, or state in any way that could reconstruct or hint at the phrase.
- **No backend/network call is required to reveal it** — this is a fully local, on-device operation, consistent with ADR-002's trust boundary (the backend has no role in, and is not consulted for, recovery-phrase reveal).

**Security tradeoff, stated explicitly**: allowing later reveal genuinely improves recoverability — a user who loses or damages their original physical backup gets a way to produce a fresh one without wiping and restoring the wallet. It also genuinely **increases the consequences of local device compromise**, since a successfully authenticated (or coerced, or exploited) reveal request now yields the same top-tier secret that non-revealability (option A) would have kept permanently inaccessible after onboarding. This ADR accepts that tradeoff deliberately, judging the harm from unrecoverable lost-backup scenarios (option A's failure mode) to be a more common and more severe practical outcome than the incremental risk added by a strictly gated reveal path.

**Biometric authentication does not make phrase exposure risk-free.** Consistent with ADR-002's Threat/Trust Assumptions, biometrics only gates *access to* the reveal operation — it does not eliminate the consequence of a successful bypass, a coerced unlock, or a fully compromised device. This flow reduces the exposure window and requires deliberate, authenticated intent; it does not make revealing the phrase a safe operation under every threat scenario in §12 of ADR-002 or §15 below.

### 6. Clipboard / share / export policy

V1 baseline, applied to the recovery phrase specifically:

- **No clipboard copy** of the mnemonic, in whole or in part.
- **No OS share sheet** invocation for the mnemonic.
- **No file export** (text file, PDF, or otherwise).
- **No QR encoding of the full mnemonic** — a QR code encoding the entire recovery phrase would be a high-value, easily-scanned exfiltration target and is explicitly not offered in V1.
- **No automatic cloud sharing** of any kind (this is also required, independently, by §12's cloud-recovery deferral).

**Screenshots / screen recording**: the product should apply available platform privacy controls where practical for the reveal screen specifically — e.g. Android's `FLAG_SECURE`, which genuinely blocks both screenshots and screen recording at the OS level for a flagged screen. iOS's equivalent protections are more limited (detection/reaction rather than a hard block). **This document does not, and the product must not, claim that software running on the device can guarantee an external camera, a screen-recording tool operating outside the app's own protected surface, or a fully compromised OS cannot capture what is displayed.** This is a reduction of risk, consistent with ADR-002's threat model, not a prevention guarantee.

### 7. BIP-39 passphrase

Analysis:

- A BIP-39 passphrase (the informal "25th word") is mixed into the PBKDF2 derivation that produces the seed — **it changes the derived seed entirely**, not just how the mnemonic is presented.
- **Every passphrase value, including the empty string, produces a valid-looking wallet.** There is no way to distinguish "the correct passphrase was entered" from "a different, plausible, but wrong passphrase was entered" except by observing whether the expected funds/history appear.
- **Forgetting or mistyping the passphrase makes the expected wallet appear silently empty** — not as an error, but as a functioning, apparently-correct, zero-balance wallet. This is a categorically different and more severe failure mode than a wrong mnemonic word (which typically fails a checksum outright).
- Interoperability/support burden: passphrase support meaningfully increases both import ambiguity (does this mnemonic have one or not?) and support-conversation complexity ("my wallet is empty" becomes far harder to triage without asking the user to confirm passphrase usage).
- Genuine security/plausible-deniability benefit exists (protects against a compromised-storage-only attacker who has the encrypted wallet but not the passphrase, and can support hidden/decoy wallets) — but this benefit accrues mainly to sophisticated users who understand the failure mode well enough to manage it safely.
- UX risk for the median user is judged to outweigh the benefit for a V1 product whose stated design principle is avoiding fake or half-understood functionality.

**Recommended V1 decision, adopted: passphrase creation is NOT exposed in V1.** No V1-created wallet uses a passphrase; every wallet Swiss Wallet generates derives its seed from the mnemonic alone.

**Import behavior — decision**: **V1 supports an optional passphrase field during import, offered but not defaulted to any assumed value, without offering passphrase creation.** Concretely: the import flow asks whether the mnemonic being restored uses an optional passphrase, and if so, accepts it as an explicit, separate input alongside the mnemonic itself; if left blank, the standard empty-passphrase derivation is used.

Justification for this choice over "V1 imports only no-passphrase wallets": silently assuming no passphrase for every imported mnemonic is exactly the silent-misinterpretation failure this task explicitly warns against — a user restoring a passphrase-protected mnemonic from another wallet would see an apparently-valid, apparently-empty wallet with no indication anything went wrong, which is a support and trust disaster with no way to self-diagnose. Explicitly asking, and accepting an optional passphrase field, avoids that failure at the cost of one additional optional input field — a small, justified addition, not a passphrase *creation* feature. **An absent passphrase input is never silently reinterpreted as anything other than the standard empty-passphrase derivation** — it is exactly what the user indicated, nothing inferred.

### 8. Import model

Conceptual V1 sequence:

```
user enters mnemonic locally
  → checksum/format validation (locally, against the English BIP-39 wordlist, §2)
  → optional passphrase handling per §7 (explicit optional field, never assumed)
  → seed derived locally
  → ADR-003 account paths derived (Ethereum m/44'/60'/0'/0/0;
    Bitcoin BIP-84 external/internal branches)
  → addresses generated
  → public chain discovery performed later (§9 — not part of import itself)
  → secure local persistence established (mechanism: ADR-005, not this ADR)
```

Hard invariants:

- **The mnemonic never goes to the backend**, in any form, at any point during import — this is a direct restatement of ADR-002's trust boundary, applied specifically to the import flow.
- **No remote "validation API."** Checksum and format validation are entirely local operations performed by Wallet Core against the local wordlist — there is no legitimate reason for a network round-trip to validate a mnemonic, and doing so would itself be a trust-boundary violation.
- **No analytics or logging** of the mnemonic, the passphrase, partial input, or any state that could reconstruct either, at any point in the import flow.
- **No autocomplete/cloud-keyboard assumptions for sensitive inputs without security review.** The mnemonic and passphrase input fields must not rely on platform text-input behavior that could leak entered words to a cloud-synced keyboard-learning cache or predictive-text history — this requires explicit platform-level configuration (e.g. disabling autocorrect/predictive text and marking the field as sensitive where the platform provides a mechanism to do so) at implementation time, reviewed as part of the eventual security review for this flow. This document does not claim any specific platform API fully eliminates this risk — only that it must be deliberately addressed, not left to default text-field behavior.

**Accepted mnemonic lengths for import**: V1 accepts **any standard, checksum-valid BIP-39 length** — 12, 15, 18, 21, or 24 words — not only the 12/24 forms discussed in §3. Rejecting a valid, checksum-correct standard-length mnemonid solely because it doesn't match V1's own 12-word generation default would be a restore-compatibility failure with no security benefit, since 15/18/21-word mnemonics are valid, if less common, BIP-39 outputs a restoring user could legitimately be holding from another wallet.

### 9. Restore / discovery model

**Recovery is not complete merely because the same seed was reconstructed.** Full recovery requires cooperation between secret recovery (§1–§8 above) and the deterministic account/address discovery already specified in ADR-003:

- **Ethereum**: the approved V1 account/address path (`m/44'/60'/0'/0/0`, ADR-003 §2) is derived directly — no scanning is needed, since V1 exposes exactly one deterministic Ethereum address.
- **Bitcoin**: both the external (`m/84'/0'/0'/0/i`) and internal/change (`m/84'/0'/0'/1/i`) branches must be restored via the address-discovery process ADR-003 §6 already defines — sequential derivation and checking per branch, governed by the conventional (not cryptographically mandated) gap limit of 20 established there. Discovery is not complete until both branches have been scanned to their gap boundaries and the current UTXO set for every discovered used address has been retrieved.

**Stated explicitly, as the governing formula for this ADR**:

> **wallet recovery = secret recovery (this ADR) + deterministic account/address discovery (ADR-003) + chain-state discovery (addresses/UTXOs/history against a live data source)**

This ADR does not implement or select the provider/indexer strategy that performs chain-state discovery — that is explicitly **Stage 4C / a future provider-architecture ADR's** responsibility. This ADR only establishes that recovery is incomplete without it, and that the discovery policy it depends on (gap limit, branch structure) is the one ADR-003 already fixed, not a new one invented here.

### 10. Lost device model

| Scenario | Recovery outcome |
|---|---|
| Phone lost | Recovery phrase, applied against the standards fixed in ADR-003 and this ADR, is sufficient to fully reconstruct the wallet (keys, addresses, and — once chain-state discovery per §9 completes — visible balances/history) on a new device, **without requiring any Swiss Wallet backend infrastructure to exist or respond.** |
| Phone destroyed | Same as lost — the phrase is the sole and sufficient recovery input. |
| Phone stolen, locked | Same recovery guarantee applies for the legitimate owner restoring elsewhere; the stolen device itself is a separate, local-compromise-resistance question governed by ADR-002's threat model and secure-storage guarantees (ADR-005), not by this ADR. |
| Phone stolen, unlocked | This is a **local key-exposure threat**, not a recovery-sufficiency question — it is governed by ADR-002's Threat/Trust Assumptions (an unlocked, stolen device already inside the trust boundary is explicitly a threat this architecture can only reduce, not fully prevent) and by the biometric-gating requirements this ADR imposes on reveal (§5). This ADR's recovery guarantee is unaffected either way: the legitimate owner can still restore from their phrase on a new device regardless of what happens to the stolen one. |

**App-specific, non-sensitive metadata that cannot be reconstructed from the seed alone** (e.g., any locally-stored preferences, display settings, or transaction labels/notes a future version might add) **must be explicitly distinguished from funds/key recovery** in any user-facing messaging. Losing such metadata on device loss is an inconvenience; it is never to be conflated with, or allowed to imply anything about, the safety of the user's funds — those two loss categories have entirely different severity and must be communicated as such.

### 11. Local backup state

Two distinct things must never be conflated:

- **A. The recovery phrase / seed itself** — a secret, subject to every protection required by ADR-002 and this ADR's reveal/storage rules, and to the secure-storage architecture ADR-005 will define.
- **B. A local "backup verified" boolean or equivalent metadata** (recording that the onboarding verification challenge in §4 was completed) — **this is not itself a security secret**, carries no ability to reconstruct or access the wallet, and **must never be treated as, or substitute for, the phrase itself.**

**The mnemonic must never be stored in `AsyncStorage`, general application preferences, or any other unprotected general-purpose persistence** — this restates the root `CLAUDE.md` and `apps/mobile/CLAUDE.md` invariant directly. The "backup verified" flag (B) has no such restriction; it is ordinary, non-sensitive application state and may be stored via whatever general-purpose mechanism the app otherwise uses for non-sensitive preferences.

**The exact secure-storage mechanism used to protect (A) is explicitly ADR-005's decision, not this ADR's.** This ADR only establishes that (A) requires that protection and (B) does not.

### 12. Cloud / social recovery

**V1 decision: deferred.** None of the following are part of V1, and none may be introduced without a future ADR that carries its own separate threat model:

- Plaintext iCloud backup of the mnemonic/seed.
- Plaintext Google/Android backup of the mnemonic/seed.
- Backend seed escrow of any kind.
- Any server-known recovery secret.
- Social recovery (guardian-based or otherwise).
- Shamir secret splitting.
- MPC-based recovery.

This is a direct restatement and formalization of `PRODUCT_ARCHITECTURE.md` §9's existing position, and of ADR-002's trust-boundary invariant that raw seed/private keys never go to the backend in any form, encrypted or otherwise, under the architecture this ADR series has established so far.

**Constraint on any future work in this area**: should a future ADR approve some form of encrypted cloud or social recovery, it **must not retroactively weaken the V1 non-custodial trust boundary** established across ADR-002/003/004 — concretely, any such future mechanism would need to be designed so that Swiss Wallet's own infrastructure never gains the ability to decrypt or reconstruct a user's seed unilaterally (e.g., client-side encryption with a key Swiss Wallet never possesses, if such a feature is ever built). This ADR does not design that mechanism; it only records the constraint any future proposal must satisfy to be acceptable at all.

### 13. Backend boundary

Restated explicitly for the recovery/backup domain specifically, consistent with and extending ADR-002:

- The backend (future NestJS service) **never receives the mnemonic.**
- The backend **never receives the seed.**
- The backend **never receives private keys.**
- The backend **never performs recovery derivation** — all mnemonic-to-seed-to-key derivation happens exclusively in Wallet Core, on-device.
- The backend **is not required to restore access to funds.** A user can fully recover their wallet with only their recovery phrase, a standards-compliant Wallet Core implementation, and access to *some* Bitcoin/Ethereum data source (which need not be Swiss Wallet's own backend — any compatible indexer/node would do, per §9).
- The backend **may later help restore non-sensitive app metadata only** (§10) — never anything that affects fund/key recovery.

**Swiss Wallet must remain recoverable even if the company or its backend disappears entirely.** This is not aspirational language — it is the concrete, testable consequence of the invariants above: recovery depends only on the user's phrase, published standards (BIP-39/32/44/84), and generically available chain data, none of which require Swiss Wallet's continued existence.

### 14. Recovery UI security requirements (future implementation — not built here)

Requirements for whichever future stage actually implements onboarding/recovery UI:

- The recovery-phrase display/reveal screen must be marked and treated as **security-critical** throughout the codebase (naming, review process, test coverage expectations).
- The phrase must be **hidden by default**, requiring an explicit reveal action even after the authenticated gate in §5 is passed — not shown automatically the instant the screen renders.
- **Re-authentication** is required per §5's rules, not assumed to carry over from a prior, unrelated authentication event.
- **Background/app-switcher privacy treatment**: the phrase must not be visible in the OS-level app-switcher snapshot or after backgrounding, per §5/§6.
- A **timeout** must return the flow to a hidden/re-authenticate state after inactivity, not leave the phrase indefinitely visible.
- **No telemetry** of any kind tied to this flow's content.
- **No debug logging** of this flow's content, including in development builds — the rule is not relaxed for non-production configurations.
- **No clipboard** interaction, per §6.
- **Accessibility implications must be actively reviewed, not silently disabled.** Screen-reader/accessibility support for a security-critical screen is a real design problem (e.g., a screen reader announcing recovery words aloud has different exposure characteristics than on-screen display) that must be explicitly considered and designed for at implementation time — disabling accessibility outright for this screen is not an acceptable default resolution, since it would exclude users who depend on it, and any final approach requires its own review.
- **Localization must never alter the BIP-39 words themselves** — only surrounding UI copy may be localized, consistent with §2's English-only wordlist decision.

No UI is designed or implemented by this ADR — these are binding requirements for whichever future implementation stage builds it.

### 15. Failure states

| Failure | Required behavior |
|---|---|
| Invalid word count | Reject locally before attempting derivation; message must state the word count is invalid, not imply the words themselves are wrong. |
| Invalid word (not in the English BIP-39 wordlist) | Reject locally; identify that an entered word is not recognized, distinct from a checksum failure. |
| Checksum failure | Reject locally; message must communicate that the word combination does not form a valid standard mnemonic — this is detectable before any chain interaction. |
| Wrong passphrase (§7) | Cannot be structurally detected — a wrong passphrase produces a different but equally "valid" seed. This surfaces only as the "valid mnemonic restoring a different/empty wallet" case below, and must be explained to the user as a possible cause when relevant. |
| Valid mnemonic restoring a different/empty wallet | **Must never be reflexively labeled "wrong recovery phrase."** A checksum-valid mnemonic with the correct (or no) passphrase, applied through the correct ADR-003 derivation, can legitimately show zero funds — because the wallet is genuinely new/unused at the currently-discovered addresses. Product messaging must distinguish this honestly from an actual input error, and may prompt the user to double-check passphrase usage (§7) without asserting the phrase itself is wrong. |
| Incomplete Bitcoin discovery | Must be surfaced as an in-progress/incomplete state (e.g. "still scanning for transaction history"), never silently presented as a final, complete balance before gap-limit scanning (ADR-003 §6) has actually finished. |
| Chain provider unavailable during restore | Must be surfaced as a network/provider failure, distinct from both a mnemonic error and a legitimately-empty wallet — the honest, never-fabricate-a-balance principle already established in `PRODUCT_ARCHITECTURE.md` §6 applies directly here: an unreachable provider must never be presented as "zero balance." |

**The unifying principle**: a wallet that is genuinely empty, a wallet whose data source is temporarily unreachable, and a wallet reconstructed from an actually-wrong secret are three different states with three different causes, and the product must never collapse them into a single ambiguous "something's wrong" message that could mislead a user into believing they've lost funds that are, in fact, safe (or vice versa).

### 16. Security / product tradeoffs

Recorded explicitly, as a permanent framing for how this entire domain must be communicated to users:

- **Non-custodial recovery means the company cannot reset the wallet for the user.** There is no "forgot password" flow, because there is no password Swiss Wallet ever held.
- **Losing the recovery secret (and any passphrase, if one was used at import) can mean irreversible loss of access to funds.** This is not a defect to be engineered away — it is the direct, necessary consequence of the non-custodial model this entire ADR series exists to preserve.
- **Support staff must never request the phrase**, under any circumstance, for any purpose (troubleshooting, verification, "confirming your identity"). Any support process that would require a user to disclose their recovery phrase is itself a phishing vector and must not exist.
- **Product UX must communicate irreversibility honestly, without ever implying Swiss Wallet can recover the funds if the phrase is lost.** This applies to onboarding copy (§4), Settings copy, and any future support-facing documentation.

**No custodial "account recovery" fallback is designed, implied, or permitted as a substitute for the recovery phrase in V1.** This is not merely undesigned — it is explicitly excluded, because any such fallback would require exactly the kind of backend-held recovery capability §12 and §13 rule out.

## Alternatives Considered

- **BIP-39 standard user backup (selected)** — see §1. The only option evaluated that satisfies both interoperability and the non-custodial invariant without introducing a new trust dependency.
- **Device-only / no mnemonic backup at all** — rejected. Would mean total, permanent, unrecoverable loss of funds on any device loss, destruction, or failure, with no path to recovery whatsoever — unacceptable for a product whose funds are real and material, not merely a demo.
- **Server-assisted recovery** (backend holds or can reconstruct any part of the recovery secret) — rejected outright. Directly reintroduces custodial trust, contradicting the non-custodial invariant stated in root `CLAUDE.md` and reaffirmed in every prior ADR in this series.
- **Encrypted cloud recovery** — deferred, per §12. A legitimate future direction, but one that requires its own dedicated threat model (key-management design, who can decrypt, what happens if the cloud account itself is compromised) that this ADR does not attempt to resolve.
- **Social / MPC recovery** — deferred, per §12. Meaningfully more complex both cryptographically and in UX terms than the baseline BIP-39 model, with no current V1 product requirement driving it; revisit only if a specific, well-justified product need emerges.
- **BIP-39 passphrase (as a default/required feature)** — deferred for creation, limited support for import, per §7. Real security/plausible-deniability benefit exists, but the silent-total-loss failure mode is judged too severe to expose to the median V1 user by default.

The V1 model accepted here — plain BIP-39 mnemonic, English wordlist, 12-word generation default, strictly-gated later reveal, no cloud/social recovery, no default passphrase — is the option set that satisfies the non-custodial invariant, maximizes standards-based interoperability, and minimizes the number of silent, hard-to-diagnose failure modes a user could encounter, without introducing any new trust dependency on Swiss Wallet's own infrastructure.

---

## Consequences

**Benefits:**
- A single, standards-compliant recovery mechanism that works even if Swiss Wallet's company or backend ceases to exist (§13).
- Interoperability with the broader BIP-39/32/44/84 wallet ecosystem, avoiding proprietary lock-in (§1, consistent with ADR-003 §11).
- A clear, non-conflated separation between the recovery secret and non-sensitive local state (§11), simplifying what future secure-storage work (ADR-005) actually needs to protect.
- Honest, explicit handling of the empty-wallet-vs-wrong-phrase ambiguity (§15) reduces the risk of a support/trust crisis caused by ambiguous product messaging.

**Costs:**
- Requiring backup verification before onboarding completes (§4) adds real friction to first-run UX — a deliberate, accepted tradeoff, not an oversight.
- Supporting an optional passphrase field at import only (§7) adds a small but real amount of import-flow complexity and support-conversation nuance ("do you know if your mnemonic has a passphrase?") relative to either extreme (no passphrase support at all, or full passphrase creation support).
- Bitcoin restore's dependence on gap-limit chain-state discovery (§9) means recovery completeness cannot be established purely offline the way Ethereum's can — a real asymmetry inherited from ADR-003, restated here as it directly affects perceived recovery UX ("is my restore actually done?").
- The later-reveal policy (§5) keeps a residual, deliberately-accepted risk surface open for the lifetime of the product, in exchange for avoiding the harsher failure mode of permanent non-revealability (§5's tradeoff discussion).

## Acceptance Invariants

1. The recovery phrase is generated only on-device.
2. The phrase/seed is never transmitted off-device, to the backend or anywhere else.
3. The phrase/seed is never logged, in any build configuration.
4. The backend is not required for recovery to succeed.
5. Standard derivation (ADR-003) allows independent recovery in any compatible implementation.
6. The recovery UI never exposes the phrase without a deliberate, freshly-authenticated user action (§5).
7. No silent cloud backup exists or is triggered automatically (§6, §12).
8. No clipboard, share-sheet, or file/QR export of the mnemonic exists in V1 (§6).
9. Passphrase policy is explicit and asymmetric by design: not offered at creation, optionally accepted at import (§7) — never silently assumed either way.
10. Restore does not depend on Swiss Wallet company infrastructure continuing to exist (§13).
11. Onboarding backup verification is required to complete onboarding in V1 — no silent or indefinite skip path exists (§4).
12. A "backup verified" flag is not a secret and never substitutes for the phrase itself (§11).

## Final ADR Decisions

| Decision | V1 Choice | Deferred / Rejected | Reason |
|---|---|---|---|
| Recovery standard | BIP-39 mnemonic → BIP-32 seed, per ADR-003 derivation | Proprietary/custom recovery format — rejected | Universal interoperability, no offsetting benefit to a custom format (§1) |
| Wordlist / language | English BIP-39 wordlist only (generation and import) | Other official BIP-39 wordlists — deferred | Ecosystem/restore compatibility, avoids localization checksum ambiguity (§2) |
| 12 vs. 24 words | 12-word generation default; 12/15/18/21/24-word checksum-valid import accepted | User-facing 12/24 generator selector — rejected | 128-bit entropy sufficient for this threat model; lower transcription/abandonment risk; no compelling reason for a user-facing choice (§3) |
| Onboarding backup | Verification required before onboarding completes; no skip path | Silent/indefinite "skip for now" — rejected | Addresses can receive funds before backup exists; irreversible-loss risk outweighs onboarding friction (§4) |
| Later reveal | Option B — revealable, strictly gated (re-auth every time, no caching, no auto-display, hidden on background) | Option A (never revealable after onboarding) — not selected | Captures most of A's security benefit while avoiding permanent loss of a lost physical backup (§5) |
| Clipboard / share / export | None of clipboard copy, share sheet, file export, or QR export in V1 | All of the above — deferred indefinitely, no current plan to add | Minimizes exfiltration surface for the highest-value secret in the product (§6) |
| BIP-39 passphrase (creation) | Not offered in V1 | Full passphrase creation support — deferred | Silent-total-loss-on-forgetting failure mode too severe for default/median-user exposure (§7) |
| BIP-39 passphrase (import) | Optional field offered during import, blank by default, never assumed | — | Avoids silently misinterpreting an externally-created passphrase-protected mnemonic as passphrase-less (§7) |
| Import word lengths | Any standard checksum-valid BIP-39 length (12/15/18/21/24) accepted | — | Restore-compatibility with mnemonics generated by other wallets; no security reason to reject valid standard lengths (§8) |
| Cloud / social recovery | Deferred entirely — no plaintext cloud backup, no server escrow, no social/MPC recovery | All forms — deferred pending a dedicated future ADR with its own threat model | Reintroduces custodial-adjacent trust; requires separate, careful design not undertaken here (§12) |
| Backend role in recovery | None — backend never receives mnemonic/seed/keys, never derives, never required for fund recovery; may later assist only with non-sensitive app metadata | Backend-assisted or backend-required recovery — rejected outright | Preserves the non-custodial invariant even if the company/backend disappears (§13) |
| Restore dependency | Recovery phrase + published standards (BIP-39/32/44/84) + any compatible chain data source | Dependency on Swiss Wallet's own backend for recovery — rejected | Recovery must not require Swiss Wallet's continued existence (§13) |
